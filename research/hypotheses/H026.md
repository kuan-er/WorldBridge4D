# H026 — Full-depth Wan14B LoRA using final block 39

## Hypothesis

The matched H023 256×256/K=16 two-rank route can use the complete 40-block
Wan2.1-14B backbone with rank-16 LoRA when the weak fourth readout is changed
from the 1.3B model's final block 29 to the 14B model's true final block 39.
Staging the native checkpoint from NAS to node-local `/tmp` should remove NAS
transfer from repeated model construction. With block-level FSDP wrapping,
two A100/A800 80 GiB cards should complete a real two-update gate before the
100,000-update run is allowed to start.

The engineering hypothesis is falsified if the full 0–39 model cannot complete
two finite BF16 optimizer updates, exceeds card capacity, or fails to produce
LoRA/adapter/decoder gradients. A passed gate is capacity evidence only.

## Fixed protocol

- Native model: all Wan14B blocks `0..39`.
- Readout: `[13,14,15,39]`, initialized to `0.3/0.3/0.3/0.1`.
- LoRA: rank/alpha 16/16, Q/K/V/O and both FFN projections, dropout 0.
- Local model root: `/tmp/worldbridge4d-models/Wan2.1-T2V-14B`.
- Two-rank target: physical GPUs 0/1, when both are exclusively available.
- All data, prompt, decoder, K=16, microbatch-2, accumulation-2, learning-rate,
  seed, schedule, and checkpoint settings otherwise match H023.

## Evidence

Implementation changes the Wan14B config to declare 40 layers, enforce final
block 39, and load the checkpoint/VAE from the local staging root. The trainer
now validates the final readout against `wan_num_layers`, preserving block 29
for the default 30-layer 1.3B configuration while requiring block 39 for 14B.
A streaming atomic staging utility copies the six diffusion shards, native
configuration/index, and byte-identical VAE to `/tmp` and records a manifest.
Staging Run `R-20260816093811-89eb3d` completed successfully in 343.5 seconds.
It atomically copied and hashed all six transformer shards, native config/index,
and VAE under `/tmp/worldbridge4d-models/Wan2.1-T2V-14B`; the local manifest
records 57,661,784,391 bytes.

The first single-GPU gate `R-20260816094943-66e88a` successfully loaded all 40
blocks from `/tmp`, passed the prior patch-embedding/FSDP failure point, and
reached the decoder upsampler. It then OOMed under B2/A2 while requesting an
additional 3.00 GiB: 75.52 GiB was allocated and 2.41 GiB reserved. This is a
real single-card capacity failure, not a loading or FSDP correctness failure.
The registered retry changes only the live microbatch to B1/A4, preserving four
clips and 64 pairs per single-GPU optimizer update while halving live decoder
pairs. Retry `R-20260816100104-b3adce` succeeded: two finite optimizer updates,
losses `0.91524/0.92997`, raw EPE `4.0134/3.3635 m`, and peak allocated memory
`75.188 GiB`. The second update took 34.75 seconds after prefetch warm-up. This
supports single-card B1/A4 capacity with about 4.1 GiB nominal headroom, but the
formal two-rank B2/A2 route still requires its own gate.

A single-card 50,000-update B1/A4 profile was registered after the gate, but it
was superseded before launch when both GPUs 0/1 became free. At user request,
the selected long run is instead the direct two-rank B2/A2 route: 50,000 cosine
horizon updates, 1,000-update warmup, K=16, eight clips/128 pairs per update,
and the existing early checkpoint milestones plus every 5,000 updates after
10,000. The user explicitly waived a separate two-rank capacity gate. This long
run intentionally uses gate bootstrap mixture statistics and the deterministic
lazy cache, so it remains experimental rather than the formal audited-shard
route.
