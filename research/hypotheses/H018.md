# H018 — Standard external dataset preprocessing and cache protocol

## Question

Can an external RGB/depth/camera/track dataset be made directly consumable by the Dense4D trainer without repeating VAE encoding, geometry decoding or coordinate-convention debugging?

## Prediction

A versioned manifest plus fixed 21x128x128 clip contract, immutable sharded sample/latent artifacts, explicit source-camera XYZ semantics, train-only coordinate statistics and mandatory geometry/latent/gradient audits will make external dataset handoff reproducible and substantially reduce startup and CPU overhead.

## Normative artifacts

- `docs/DATASET_PREPROCESSING_PROTOCOL_V1.md`
- `docs/dataset_manifest_v1.schema.json`

## Required handoff

The next preprocessing agent must produce a manifest, disjoint split JSONL indexes, sharded deterministic Wan clean latents, source-frame coordinate statistics and either rigid-instance annotations or dense source-grid XYZ trajectories. It must run every validation gate in the protocol and leave a ready-to-run training YAML. A dataset with only RGB and depth may claim diagonal pointmap training but must not fabricate arbitrary-source tracking labels.

## Evidence

The current H017 run showed that a persistent full-data clean-latent cache is useful, while the original synchronous geometry path serialized the GPU behind CPU target construction. H017 subsequently enabled eight-worker, depth-two source-centric geometry prefetch, pinned transfers, GPU-only EPE diagnostics and explicit W&B `global_step`. The real two-step full-Wan gate `R-20260810131558-e054df` passed with finite Wan/adapter/decoder gradients and correct W&B history rows at steps 1 and 2.
