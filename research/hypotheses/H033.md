# H033 — decoder-native camera token + per-frame ray field

## Hypothesis

The H032 camera readout did not learn: at 196500–200000 its pose metrics sat at (or below) the
trivial "identity rotation + zero translation" baseline, and its FoV supervision only recovered a
per-clip constant. Two measured causes were identified:

* the standalone head read a **16×16 average-pooled** copy of the structured features, and
* its loss was numerically flat — with the point-cloud sigma (5.62 m) the identity and
  best-constant pose predictors had essentially identical translation loss
  (Kubric 0.02898012 vs 0.02897891), while the camera weights themselves moved 27× from init.

H033 therefore replaces the module, not just its weights:

1. **Pose** is read from **one camera token appended to the decoder's own pair-query sequence**, so
   it attends to the same full-resolution structured memory (32×32 or 64×64) as the XYZ head and is
   read out by a plain MLP + two linear heads (the 4RC `camera token → MLP` shape).
2. **Intrinsics** are read as a **per-frame unit ray field** from the **diagonal pair's pixel
   tokens**, supervised by GT rays and decoded to a skew-free pinhole K. This is strictly more
   general than two FoV numbers (principal point, and in principle distortion, become expressible)
   and it removes the source-dependence question by construction.
3. **Translation supervision** is normalised by the measured camera-scale medians
   (Kubric 0.30 m, PointOdyssey 0.032 m, Dynamic Replica 0.020 m) instead of the point-cloud
   coordinate sigma.

Deleted from H032: `memory_projection`, `spatial_projection`, `memory_time`, `cross_attention`,
`cross_mlp`, `temporal` transformer, `pose_mlp`, `fov_mlp`, the 21 pose queries, the 21 intrinsic
queries and the source/target/relative-time embeddings — seven modules in total.

## Preserved contract

* K10 sampling: 80 pairs/update, one forced diagonal + nine non-diagonal targets per source.
* `(source,target)` relative pose is still modelled **directly** per pair (`T_source<-target`), never
  composed from a shared global pose.
* Per-frame intrinsics remain **source-independent**: the ray head only ever sees the diagonal pair,
  whose query content carries `target_time(t)` and never `s`.
* GT rays always use the real principal points; predicted intrinsics never build a target.
* Non-rigid PO annotation bases still mask only their own pose labels; clip, XYZ, GT rays and the ray
  field keep training.
* Camera LR 1e-4 with the 500-update warmup anchored at 196000; trunk, optimizer groups, seeds,
  mixture and counters unchanged.
* Trunk parameters are inherited from the H032 210000 endpoint; only the deleted `camera_head.*`
  parameters and their Adam states are dropped (`finetune_drop_prefixes: ['camera_head.']`).

## Readout details

```
pixel tokens  [B,P,Q,D]        Q = 32x32 (256px) or 64x64 (native512)
camera token  content(s,t) + camera_pose.token     -> appended at Q (RoPE coordinate = grid centre)
after 5 x CrossAttentionBlock:
  pose:     camera_pose(mlp)  -> fc_t [B,P,3] metres, fc_qvec [B,P,4] XYZW -> rotation
            diagonal forced to I / 0 (never supervised)
  rays:     camera_rays(pixel token of the diagonal pair, pixel-centre PE) -> [B,3,G,G] unit dirs
```

`CameraOutput.decode_pinhole` divides the ray by `-d_z`, so `p_x = u/fx - cx/fx` and
`p_y = -v/fy + cy/fy` are two weighted linear least-squares problems. Degenerate (near-flat) fields
are flagged invalid rather than reported as huge focal lengths.

Loss: `diagonal_xyz` 0.5, `offdiagonal_xyz` 0.5, `diagonal_ray` 0.1 (GT-ray projection of the
diagonal pointmap), `ray_field` 0.1 (angular, `1-cos`), `front` 0.01, `pose_rotation` 0.1,
`pose_translation` 0.1 (camera-scale normalised).

## Evidence so far

* Full CPU suite: **576 tests pass** (27 camera tests, rewritten for the new contract).
* GT ray probes: rays at the query grid decode `fx/fy` within `1e-3` relative error, including an
  intentionally offset principal point (131.4, 98.2) which is recovered exactly.
* A layout bug (channel/token axes interleaved by a bare `reshape` instead of `transpose`) was caught
  by the unit-norm ray test before any GPU run.
* Real GT `unit_rays_at` matches the existing full-resolution `unit_source_rays` convention.
* Fresh camera parameters: 17 tensors / 926,218 parameters (was 51 / 1,414,409).

## GPU smoke (200000 -> 200020, physical GPU3/5)

A bounded 20-update migration smoke ran on the two operator-authorized GPUs and
passed end to end (`R-20260925154410-9df9c3`, checkpoint review
`H033_SMOKE_REVIEW_OK`, sha `24e38b20c18e934aa5b920411772148c2e99577b1097f02d000a0ab045695f28`).

* Migration: 51 old `camera_head.*` tensors and their Adam states dropped, 17 fresh
  camera tensors added; 1053 retained + 17 fresh = 1070 optimizer states; 6 groups; 2 RNG ranks.
* Data path: one full 20-update mixture cycle added exactly kubric+80, pointodyssey+40,
  dynamic_replica+40 clips through the cycle-free loader, and `train/pairs=80`
  with `diagonal_pairs=8` per update.
* Camera readout learns: `ray_field` 1.2015 -> 0.0169, `ray_angle_deg` 103.3 -> 9.33,
  `decoded_valid_fraction` 0.125 -> 1.0, `focal_relative_error` 0.647 -> 0.142,
  `rotation_deg` 14.5 -> 9.14 in 20 updates.
* Peak memory 63.519 GiB at both ends, matching H032's 63.5 GiB: the new design adds no memory.
* Checkpoint saved and independently reviewed: model finite, Adam step +20 on every
  parameter, counters exact, 2 RNG ranks.

Caveats, stated plainly: GPU3 is ECC-degraded (900 volatile uncorrectable DRAM errors,
66 uncorrectable row remaps, pending/failure remap state) and the operator explicitly
overrode the health gate, so these numbers are evidence that the *code path* works, not
that the run is numerically trustworthy. `xyz_loss` moved 0.0419 -> 0.0634 and
`raw_epe_m` 0.280 -> 0.378 over the 20 steps, which is inside per-batch noise but worth
watching in the real run now that the camera gradient is much stronger.

## Open items

* The gate needs the H032 210000 endpoint, which the running K10 continuation has not reached yet.
* The decisive measurement — a **fixed-clip evaluation** on held-out clips comparing predicted pose
  and intrinsics against the identity and constant baselines — still has to be built. Without it the
  H033 numbers are train-batch metrics, exactly like the H032 ones that misled us.
* A linear probe from the decoder memory to GT pose, and an 8-clip overfit test, remain the cheapest
  way to separate "features lack pose information" from "loss/optimisation".

## Risks

* Ray supervision appears only for the frames that happen to be sampled as source (≈8 frames per
  update), which is sparser per-frame coverage than the old 21 FoV queries.
* Camera gradients still flow into the shared trunk (no detach); the translation term now has a much
  larger effective gradient, so `train/xyz_loss` must be watched for regressions.
* The pose branch is still a per-pair regression; if the memory does not identify per-pair motion it
  will settle at the conditional mean again, and only the geometry route (ray field + pointmap) can
  then carry the camera parameters.
